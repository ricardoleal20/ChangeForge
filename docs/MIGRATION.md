# Migrating from ChangeForge

The product and primary CLI are now ReleaseWeave. The upstream remains `https://github.com/ricardoleal20/ChangeForge`; no GitHub repository or registry package has been renamed remotely.

## Executable and installation

Build with Cargo instead of the experimental Python/Poetry/Maturin chain:

```sh
cargo install --path . --locked --bin releaseweave
```

Install `--bin changeforge` as well if existing scripts need the old executable. Both names run the same command parser. Use `--help` to see noninteractive flags and aliases.

## Configuration

An existing standalone `changeforge.toml` or `[tool.changeforge]` section in pyproject.toml remains readable. The adapter treats `version_path` as synchronized files belonging to one package. All their versions must match; a mismatch is an error.

`init --yes` migrates standalone changeforge.toml. For embedded configuration, create releaseweave.toml manually using the README example, preserving your configured changesets_dir and changelog paths. The new config takes precedence.

Use `additional_manifests = ["pyproject.toml"]` inside a package to synchronize another supported manifest with its primary manifest. The primary manifest is selected by `manifest`. The optional `version_key` overrides its TOML field, for example `tool.poetry.version`. JSON manifests always use the top-level version.

AI, templates_dir and commit_on_create options are not imported: the repaired PoC records explicit messages and leaves Git commits to the developer. Existing changesets and changelogs are preserved.

## Changesets

Legacy [changeset]/[changes] TOML documents work in single mode. Stored version strings are ignored because they can become stale between PRs; their change_type is applied to the current version at release time. The description becomes the changelog note.

For monorepos, migrate every pending file to an explicit message and package-to-bump mapping:

```toml
message = "Fix API timeout"
[releases]
acme-api = "patch"
```

Legacy changesets are rejected in monorepo mode to avoid assigning them to the wrong package.

## Workflows

Replace the old bump_version.yml/release_on_merge.yml workflows with the files generated by `init --yes --github`; retaining both would run conflicting release flows. The previous Python wheel-publishing workflow is removed from this checkout. GitHub releases contain per-package notes and tags; registry publishing requires its own later integration.

After upstream integration, pin the consumer action to that commit rather than an unreviewed branch. Existing repository URLs and historical CHANGELOG entries intentionally retain the old name.
